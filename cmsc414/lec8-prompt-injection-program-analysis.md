# Prompt Injection and Program Analysis

## Prompt injection defenses
- Reminder: The issue in prompt injection is that data is treated as instructions
- Classic defenses such as principle of least privilege, separation of privileges, fail-safe defaults, and defense in depth are applicable to prompt injection

### CaMeL
- CaMeL is a "provably secure defense" against prompt injection which has the following properties:
    * Control-flow integrity (prevents attacks from hijacking or redirecting the flow of execution)
    * Prevents unauthorized data flows (prevents attacks from altering the flow of the data)
- Control flow is maintained via programming, i.e. a privileged LLM generating program structure without looking at untrusted data
- Data flow is fixed by tracking data dependencies and security policies, i.e. a quarantined LLM (which cannot alter program flow) takes the code generated by the privileged LLM and inserts the untrusted data into it for execution
- Security policies are used to track sources and data with metadata that labels sensitivity, trust, etc.
- CaMeL can prevent ALL prompt injections within the program's threat model (primarily indirect prompt injections). It is vastly more effective than heuristic defenses
- Unfortunately CaMeL introduces a tradeoff between security and utility, with LLM models that implement it experiencing a slight dip in performance capability. Additionally, CaMeL introduces a roughly 3x token overhead, making implementation monetarily expensive
- CaMeL also does not deal with image processing capacity
- **Takeaway: Giving an LLM privileges and untrusted data is dangerous, and heuristic defenses for prompt injection don't work. Thus, the best approach is to adapt ideas from software security**

## Software security bugs
- Dealing with security bugs entails complete mediation, or monitoring the system at runtime to detect and prevent bugs/exploits
- Sometimes bugs are unavoidable, and as such it is important to design the system in such a way that damages are minimized
- Automatically finding and fixing bugs can be done even without source code access

### Sandboxing
- A security technique which isolated code execution in a controlled environment to prevent it from affecting the broader system
- Also allows for limiting of privileges
- Useful for isolating potentially malicious code to examine its behavior
- Untrusted code in a sandbox only has access to I/O and system resources via a connection to the underlying OS
- Examples:
    * Chromium runs each webpage's rendering engine in a sandbox, restricting kernel API calls and disallowing reads/writes outside of the sandbox
    * Native client (NaCl) in the Chrome browser runs x86 in a sandbox. Control flow integrity (CFI) ensures that all control transfers in the program text only target instructions identified during disassembly

### Automatic bug detection (ADI)
- The main challenge with ADI is predicting control flow, particularly when external input is involved
- The earlier a bug is found, the less expensive it is to fix

#### Static analysis
- Inspects code and runs automated methods to find errors and/or gain confidence about their absence
- Tries to aggregate the program behavior over a large number of paths without explicitly enumerating them
- Has a high false positive rate due to tracing every possible program flow variation

#### Dynamic analysis
- Runs code, possibly under instrumented conditions, to see if there are likely problems
- Enumerates paths but avoids redundant ones
- Executes code with real input but may miss vulnerabilities

#### Comparison
- Static analysis can consider all possible inputs and can prove their absence in some cases, but dynamic analysis requires a test input and cannot prove the absence of bugs
- **Soundness**: If an analysis says there are no bugs, are there actually no bugs?
- **Completeness**: If there are actually no bugs, does the analysis successfully identify that there are none?
- Unfortunately an analysis cannot be both complete and sound, only one, the other, or neither

#### Control flow analysis
- Traces the program to discover its control flow
- Presents results in the form of a control flow graph (CFG) `G = (N,E)` where a node is a block of code with a single exit point and no internal control flow, and an edge is a control transfer between blocks of code
- CFGs are used to propagate information between nodes (basic blocks) as well as in dynamic analysis in the case of fuzzing

#### Data flow analysis
- A technique for gathering information about the possible sets of values calculated at various points in a program
- At each point in the program, what data has been written (and not overwritten) is enumerated
- Can be useful for detecting many security vulnerabilities, e.g. when an untrusted or malicious input reaches a sensitive program point

#### Implementation
- Most modern compilers perform several types of analyses for code optimization, e.g. [LLVM](https://llvm.org) where users can specify different types of analyses

#### Fuzzing
- Involves providing invalid, semi-valid, unexpected, or random data inputs to a program
- One version, called *blackbox fuzzing* involves providing random input to a program, akin to a monkey at a typewriter. The goal is to see if such random inputs can elicit incorrect behavior such as crashing from a program
- Blackbox fuzzing is easy and has a low cost for the programmer, but is not particularly efficient as usually the set of inputs that will successfully crash the program is much smaller than the set of all possible inputs
- Modern fuzzing involves generating and inputting slightly anomalous test cases into a program to attempt to elicit incorrect behavior. Inputs are usually file based or network based
- **Mutation-based fuzzing**: Involves taking a valid input and mutating it to make it invalid before entering it into the program. Little or no knowledge of the structure of the inputs is known, and inputs are added to existing valid inputs
